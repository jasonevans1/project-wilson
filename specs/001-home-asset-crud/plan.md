# Implementation Plan: Home Asset CRUD

**Branch**: `001-home-asset-crud` | **Date**: 2026-02-02 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `/specs/001-home-asset-crud/spec.md`

## Summary

Deliver full CRUD for home assets: create, list, detail, update, archive, and restore. The feature introduces the first domain model in Wilson — an `Asset` entity owned by the authenticated user, with a fixed category set and an active/archived lifecycle. All UI is reactive (single route, Livewire component tree). No permanent deletion is permitted.

## Technical Context

**Language/Version**: PHP 8.3
**Primary Dependencies**: Laravel 12, Livewire 4, Flux UI Free v2, Laravel Fortify v1
**Storage**: MariaDB 10.11 (via Laravel Eloquent; migrations only)
**Testing**: Pest 4 (feature + unit), Playwright (E2E — out of scope for this plan)
**Target Platform**: Web (Laravel 12 full-stack)
**Project Type**: Web application (single Laravel monolith — no frontend/backend split)
**Performance Goals**: Standard web-app responsiveness; asset list loads and filters reactively with no full-page reload.
**Constraints**: All queries scoped to authenticated user (data isolation). No `DB::` usage. Enum-backed categories and status. Validation in Concern trait. Pint formatting enforced.
**Scale/Scope**: Single-user asset inventory. Expected asset count per user: tens to low hundreds. No pagination pressure at launch, but paginated query is included for forward-compatibility.

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-checked after Phase 1 design — all items pass.*

- [x] I. Modularity: each new module has a single, declared purpose
      — `AssetList` (list + state), `AssetForm` (create/update form), `AssetDetail` (read + archive/restore). Each component maps to one user story group.
- [x] II. Separation of Concerns: business logic lives outside controllers
      and Livewire views; validation is in Form Requests
      — Validation lives in `AssetValidationRules` Concern (matches existing pattern). No controllers introduced. Views are pure Flux markup + wire directives.
- [x] III. High Cohesion: related domain logic is grouped; no cross-domain
      files added without justification
      — All new files live under `app/Livewire/Assets/`, `app/Enums/`, and the single `Asset` model. Enums are shared across the domain but each has one purpose.
- [x] IV. Information Hiding: new public interfaces are minimal; internal
      helpers are protected/private; all types are declared
      — Livewire public properties and actions are exactly what the view needs. Validation methods in the Concern are `protected`. All methods have typed parameters and return types.
- [x] V. Appropriate Coupling: dependency direction flows inward
      (domain ← application ← infrastructure); no circular dependencies;
      eager loading applied where relationships are traversed
      — Asset has no relationships to eager-load (it is a leaf entity for now). User → Asset relationship exists but is only used for scoping, not for rendering nested data. No circular deps.
